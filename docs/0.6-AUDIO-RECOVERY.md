# 0.6 visitor audio and light recovery

The stream still uses one authoritative native DSP engine. Guests receive Opus
and scene deltas over the existing authenticated WebSocket through Umbrel.
Robot geometry and animation are rendered locally; only controls and DSP phase
are synchronized, rather than streaming animation frames.

## Findings

A real private-session test through the public live address observed a **603 ms
delivery pause**. Audio source frame numbers remained contiguous: the audio was
arriving in bursts. The WASM visitor decoder previously admitted only twelve
20 ms packets at once (240 ms); the WebCodecs path allowed twenty-five (500 ms).
Both could discard part of a burst after a stall. Lowering bitrate did not
increase either time budget.

This demonstrates a loss mechanism, not proof that visual bandwidth caused the
pause. Rendering stalls, TCP/proxy buffering and connection jitter can all affect
delivery. The added HUD measurements help distinguish bandwidth from recovery.

## Changes

- Both decoders accept up to 128 queued packets (2.56 seconds), still bounded.
- The worklet grows its recovery buffer after starvation, up to 600 ms, rather
  than repeatedly restarting with the same insufficient budget. Initial buffers
  remain 80 ms for responsive performers, 180 ms for ordinary playback and 300 ms
  for data saver. Network delay adds to these budgets. Up to about 2.5 seconds of
  queued audio is retained for recovery; this capacity does not impose a fixed
  2.5-second delay. The HUD reports actual queued audio when larger than the
  target refill budget.
- A stable, healthy speaker owns the audio-aligned visual clock. A second
  speaker rebuffering cannot repeatedly reset all light timing. Stalled or stale
  playback clocks release visuals to the newest scene instead of freezing them.
- The relay encodes only qualities actually requested by connected listeners.
  One low-quality listener no longer requires three simultaneous Opus encoders
  per source. Different listeners may still request different qualities.
- Visual writes are coalesced while a previous scene is being compressed/sent,
  and wait for a smaller socket backlog. Scene deltas retain each client's own
  baseline when frames are skipped.
- Visitor HUD reports total stream KB/s, audio payload KB/s, playback buffer and
  recovery status. Audio payload excludes WebSocket framing; total includes it
  and reflects compressed visual traffic. Initial asset downloads are separate.
- Picking a non-module collider no longer emits repeated missing-metadata/nil
  errors in the host log.

## Verification and limits

`show-web/mobile-audio.test.mjs` sends a two-second burst through the actual visitor
WASM decoder and checks that every packet reaches playback in order.
`show-web/show-worklet.test.mjs` simulates twenty seconds of repeated 220 ms
delivery bursts and checks that silence stops after adaptation. Clock tests
exercise secondary-speaker recovery and stale-clock fallback.

Run `node --test *.test.mjs` in `show-web` for the full suite. Run:

```powershell
python scripts/check_show.py --godot .tools/Godot/Godot_v4.5.1-stable_win64.exe --build dist/embedded-0.6-audio-20261020 --opus --visual-stage
```

The integration listener exercises the real native publisher, relay Opus encoder,
WASM decoder and playback worklet with animated stage objects and a deliberate
700 ms host UI stall. It reports source frame gaps and silent playback blocks,
not just packet arrival. Private live-route validation also exercises Umbrel.
The listener runs the worklet in a VM; it does not measure physical headset audio
output, browser WebCodecs behavior or the user's exact patch and remote network.

Buffering cannot prevent the initial interruption when a pause exceeds all audio
already received. Adaptation trades extra audible latency for continuity. Long
or sustained congestion can still cause interruptions. Separate audio transport
or WebRTC would be a subsequent measured architectural change, not part of this
fix.

Restart the 0.6 launcher and reload visitor pages to load the updated relay,
decoder and worklet. The 0.5 launcher/build and existing personal patches remain
separate.

## Follow-up: audio r2

The first recovery change did not fix repeated playback starvation. A subsequent
60-second simulation reproduced **72.37% silent playback after warm-up** with a
600 ms delivery pause every three seconds. The queue's 850 ms duration cap
discarded unplayed blocks while leaving the playback clock behind those blocks.
The fixed-size cap and adaptive refill delay therefore fought each other. The
old "more than one second from playback" discontinuity check could also mistake
a continuous burst for an engine restart.

When trimming unplayed audio, the worklet now advances its clock to the first
retained frame. Source resets are identified from incoming frame discontinuity
rather than distance from delayed playback. Memory remains bounded. The same
simulation now has **0% silence after warm-up**; repeated 600 and 800 ms stalls
also pass at 44.1 and 48 kHz output. A separate overflow test checks resuming
retained audio after the queue limit is exceeded. A recovery may skip old audio to regain the
bounded live timeline; it cannot eliminate the initial network interruption.

The live test previously excluded silence when no packet had arrived in 150 ms
or when the latest recovery anchor was in the future. That hid relevant outages.
It now counts both network outages and recovery refills, excluding only initial
startup and explicit host shutdown. Longer tests are available with
`CARDINAL_SHOW_TEST_HOLD_SECONDS` (up to 30 extra seconds).

The public worklet URL is revisioned and the visitor audio status includes
**audio r2**. Restart the 0.6 relay and reload an already-open visitor tab; using
the same online URL is correct. Both the public bundle and worklet were checked
through Umbrel against the updated local files.

Umbrel reported a Raspberry Pi 5 with 8 GB RAM, normal temperature, about 4.9 GB
RAM in use and approximately 14% total CPU during the one-visitor test. These
snapshots show available capacity; they do not rule out intermittent network or
proxy delays. No hardware replacement is indicated by this playback defect.

## Public-route comparison and optional extra buffering

Matched tests against the PC relay and the Umbrel LAN endpoint observed maximum
packet gaps around 100 ms. The public HTTPS route sometimes paused for 2.33
seconds with contiguous source frames. The stricter adaptive-mode public test
still recorded 5.33% silent blocks. This isolates a delivery problem along the
public route, without identifying a particular Cloudflare or ISP component.
Temporarily forcing Cloudflare Tunnel HTTP/2 did not reliably improve continuity;
the original tunnel settings were restored. Disabling WebSocket compression also
failed to remove the pauses and increased traffic; compression remains enabled.

Visitors can now choose **Audio buffering → Extra stable** in the audio settings.
This starts with about 2.5 seconds buffered, independently of collaboration and
data-saver settings. It deliberately delays audio and synchronized lights, so it
is a continuity workaround rather than suitable low-latency musical monitoring.
Adaptive remains the default. Visual history is retained during startup/recovery
so lights can follow delayed playback when its clock becomes available.

The suite contains 85 passing tests, including queue overflow, long delivery
bursts, stable-mode preferences and visual history during audio startup. The
integration listener can select this mode with
`CARDINAL_SHOW_AUDIO_BUFFER=2.5`. It counts outages and refill silence, rather
than hiding them. A future dedicated real-time media transport should be assessed
for interactive performance; increasing Pi CPU capacity is not supported by the
current measurements.

The final 60-second public-route check with Extra stable passed: two speakers,
4,058 packets, no source frame gaps or decoder errors, and 2 silent blocks out
of 28,934 rendered blocks (about 0.007%). The maximum delivery gap in that run
was 539 ms; this single run does not establish immunity to the larger pauses
seen in earlier tests. The native fixture streamed for roughly 40 seconds and
included animated visuals and a deliberate UI stall.
